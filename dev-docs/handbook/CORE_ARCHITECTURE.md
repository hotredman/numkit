# Архитектура и инженерные решения ядра `numkit`

`numkit` — это высокопроизводительный встраиваемый интерпретатор и вычислительный движок для матрично-ориентированного скриптового языка (совместимого с MATLAB/Octave), реализованный на современном C++17. В отличие от традиционных монолитных интерпретаторов, ядро `numkit` спроектировано вокруг принципов жесткой слоистой изоляции, детерминированного управления памятью и гибридного исполнения.

В этой статье подробно рассматривается устройство **ядра `numkit`**: модель значений, управление памятью, слоистая архитектура, конвейер исполнения (Dual Engine), подсистема отладки и объектная модель. Библиотечный слой (`toolboxes`) остается за рамками статьи.

---

## 1. Фундаментальный архитектурный инвариант: `core ⊥ everything`

Ключевым проектным решением `numkit` является строгая ортогональность интерпретатора (`core`) и численного/библиотечного слоя. Архитектурный инвариант формулируется следующим образом:

> **`core` ⊥ чистый вычислительный слой.** Вычислительные библиотеки не зависят от интерпретатора и виртуальной машины. Зависимость от `core` разрешена исключительно модулю связывания `runtime` и регистратору `bundle`.

```
                value / fs / ops            ← L0/L0.5: фундамент (без core)
               ↙                    ↘
   core (Engine, AST, VM,       io · math · lang · toolboxes
         Parser, Environment)     ← L2: чистые вычисления (без core)
               ↘                    ↙
         runtime (eval, workspace, save/load, reflection)
               ↓
         bundle  (StandardEngine, регистрация встроенных библиотек)
```

### Практическое следствие: Engine-Free C++ API
Благодаря изоляции вычислений от `Engine`, любой C++-проект может использовать численные алгоритмы `numkit` как обычную C++17-библиотеку:
- Вызовы математических или цифровых функций (например, `math::roots`, `signal::fft`) не требуют инициализации интерпретатора (`Engine`), парсинга или накладных расходов виртуальной машины.
- Операции ввода-вывода (`io::csvread`, парсеры MAT-файлов) работают поверх абстракции файловой системы (`FsContext`) и памяти (`memory_resource`) напрямую на уровне C++.

## 2. Подсистема значений и управление памятью (`Value` Substrate — L0)

В основе всей системы лежит класс `numkit::Value` — универсальный контейнер для данных скриптового языка.

### 2.1. 16-байтовый тегированный указатель (`Value`)
Для минимизации аллокаций и оптимизации работы с кешем процессора экземпляр `Value` занимает ровно 16 байт и имеет следующую структуру:

```cpp
class Value {
    double scalar_;    // 8 байт: inline-значение для скаляра
    HeapObject* heap_; // 8 байт: указатель на кучу или сигнальный тег
};
```

Кодирование состояния в поле `heap_`:
* `heap_ == nullptr` — **скалярное число `double`**. Значение хранится непосредственно в `scalar_`. **Аллокации на куче равны нулю.**
* `heap_ == emptyTag()` — пустая матрица (`[]`) или неинициализированный слот.
* `heap_ == logicalTrueTag() / logicalFalseTag()` — логические скаляры `true` и `false`.
* `heap_ == deletedTag()` — сигнальная метка удаления (tombstone), используемая при индексированном удалении (`A(2) = []`).
* Любое другое значение — указатель на объект в куче (`HeapObject*`).

### 2.2. Copy-on-Write (COW) и `HeapObject`
Нескалярные данные (матрицы, N-мерные массивы, `cell`-массивы, структуры, объекты, указатели на функции) хранятся в структуре `HeapObject`.

```
Value (16 bytes)
 ├─ scalar_
 └─ heap_ ──► HeapObject
               ├─ atomic<int> refCount
               ├─ Dims dims (формат Column-Major)
               ├─ DataBuffer* buffer (числовые массивы)
               ├─ vector<Value>* cellData / structArray (cell, struct)
               └─ memory_resource* mr
```

* **Атомарный счетчик ссылок (`std::atomic<int> refCount`)**: при присваивании (`B = A`) копируется только 16-байтовый дескриптор, а счетчик `refCount` увеличивается. Фактическое копирование буфера памяти (Deep Copy) происходит лениво — только при попытке модификации (`makeUnique()` перед мутацией).
* **Column-Major Layout**: элементы матриц располагаются в памяти по столбцам (стандарт MATLAB/Fortran/BLAS/LAPACK), что обеспечивает прямую совместимость с высокопроизводительными численными библиотеками без переупорядочивания.
* **Полиморфные аллокаторы C++17 (`std::pmr::memory_resource*`)**: каждый объект памяти в системе ассоциирован с аллокатором. Встраивающие приложения могут передавать собственные пулы, арены или специализированные аллокаторы в `Engine`, полностью контролируя потребление и фрагментацию памяти.

## 3. Слоистая архитектура и статический контроль связей

Ядро и сопутствующие подсистемы строго разделены на направленный ациклический граф (DAG) слоев. Автоматический линтер `tools/check_layering.py` проверяет все исходные файлы при каждой сборке без исключений.

### 3.1. Архитектурные уровни
1. **L0 (`value`, `fs`)**: базовые типы данных (`Value`, `FnHandle`, `Dims`) и абстракция файловой системы (`FsContext`, разрешение путей и виртуальная ФС).
2. **L0.5 (`ops`)**: ядро численных примитивов. Здесь располагаются низкоуровневые вычислительные ядра: SIMD-операции, FFT, генераторы случайных чисел, линейная алгебра и алгоритмические ядра решателей (Рунге-Кутта, Брент, Нелдер-Мид, Левенберг-Марквардт).
3. **L1 (`core`)**: интерпретатор. Включает лексер, парсер, AST, байткодовый компилятор, виртуальную машину (`VM`), fallback-интерпретатор (`TreeWalker`) и менеджер окружения (`Environment`).
4. **L2 (`math`, `lang`, `io`, `toolboxes`)**: доменные библиотеки, работающие исключительно поверх L0/L0.5.
5. **L2 (`runtime`)**: связующий мост между вычислениями и движком (`eval`, инспекция workspace, `save`/`load`, рефлексия `str2func`/`func2str`).
6. **L3 (`bundle`)**: сборка и регистрация функций в глобальный реестр (`StandardEngine`).

### 3.2. Декаплинг алгоритмов и численных решателей (Solvers 3-Way Split)
Традиционно в интерпретаторах численные решатели (например, `fzero`, `ode45`) тесно переплетены с вызовом функций интерпретатора. В `numkit` реализовано 3-стороннее разделение:
* **Вычислительное ядро (`ops`)**: чистый C++-алгоритм, принимающий параметризованный интерфейс `FnHandle`. Не знает про `Engine`.
* **Библиотечный API (`toolboxes/optim` или `ode`)**: парсинг аргументов из `Value`, формирование структур вывода. Не знает про `Engine`.
* **Адаптер обратного вызова (`runtime`)**: мост, преобразующий анонимную функцию MATLAB (`@objfun`) в вызов внутри виртуальной машины.

## 4. Конвейер трансляции: Dual Engine (VM + TreeWalker)

Выполнение кода в `numkit` проходит через несколько фаз:

```
Исходный код ──► Lexer ──► Tokens ──► Parser ──► AST ──┬──► Compiler ──► Bytecode ──► VM (Fast Path)
                                                       │
                                                       └──► TreeWalker (Fallback / Reference Engine)
```

### 4.1. AST и управление памятью
Парсер рекурсивного спуска строит абстрактное синтаксическое дерево (AST). Для минимизации накладных расходов узлы AST управляются через `std::unique_ptr<ASTNode>`. Использование `std::shared_ptr` ограничено только телами функций, которые сохраняются в реестре `Engine` на длительное время.

### 4.2. Дуальный движок исполнения
`numkit` содержит два независимых вычислительных бэкенда:
1. **Bytecode VM (Основной быстрый путь)**: компилятор преобразует AST в компактный байткод с таблицами констант и картами исходного кода (source maps). Виртуальная машина исполняет байткод с минимальным оверхедом на диспетчеризацию.
2. **TreeWalker (Резервный и эталонный путь)**: прямой обходчик AST. Автоматически активируется как fallback при исчерпании регистров компилятора или специфических ошибках кодогенерации.

### 4.3. Гарантия корректности (`DualEngineTest`)
Наличие двух движков требует абсолютной семантической идентичности. Вся тестовая база (`numkit_gtest`, более 11 000 тест-кейсов) запускается через фикстуру `DualEngineTest`, которая выполняет каждый тест параллельно на Bytecode VM и на TreeWalker, сверяя результаты до бита.

## 5. Нерекурсивная паузабельная виртуальная машина и отладка

Одной из самых сложных инженерных проблем в скриптовых движках является реализация полноценного отладчика (breakpoints, step over/into/out, инспекция и выполнение выражений в паузе) в кроссплатформенном окружении, включая WebAssembly в браузере.

### 5.1. Явный стек фреймов на куче (`CallFrame`)
Вместо использования системного C++-стека вызовов (рекурсивных вызовов функции `execute`), виртуальная машина `numkit` реализует **нерекурсивный цикл исполнения**. Стек вызовов моделируется явной структурой `CallFrame`, выделяемой в куче:

```cpp
struct CallFrame {
    const Bytecode* code;
    size_t ip;
    Environment* env;
    // Локальные регистры и временные значения
};
```

Благодаря отсутствию привязки к C++-стеку, состояние исполнения (`DebugSession`) может быть **заморожено в любой точке** и сохранено. Это позволяет отлаживать скрипты в WebAssembly без использования тяжелых костылей вроде Emscripten Asyncify, файберов или отдельных нативных потоков.

### 5.2. Паузабельные обратные вызовы (Pausable Callbacks)
Когда встроенная функция C++ вызывает пользовательский код на MATLAB (например, `cellfun(@f, X)` или методы `classdef`), пользовательский код обязан выполняться на виртуальной машине, чтобы отладчик мог останавливаться внутри коллбеков.

В ядре реализовано три механизма паузабельности (описанных в `CALLBACK_PAUSABILITY.md`):
1. **In-Bytecode Frame-Push (Опкоды)**: для операций, встроенных в синтаксис (методы `classdef`, перегрузка операторов, вызовы `obj(x)`), VM помещает новый фрейм прямо в стек `CallFrame` и бесшовно продолжает цикл исполнения.
2. **C++ State Machine (`CallbackBuiltin` / `LoopContinuation`)**: для итеративных функций с плоским циклом (`cellfun`, `arrayfun`) создается конечный автомат. VM выполняет одну итерацию пользовательского коллбека, возвращает управление автомату C++, который собирает результат и инициирует следующий шаг.
3. **Встроенные `.m`-обертки (`registerBuiltinMSource`)**: для сложных адаптивных алгоритмов (например, `fzero`), где следующий шаг нетривиально зависит от результата предыдущего, управляющая логика реализуется на скриптовом языке и компилируется в стандартный байткод, что дает отладку «из коробки».

## 6. Объектная модель и окружение (`Environment`)

### 6.1. Области видимости и замыкания
Переменные хранятся в иерархии `Environment` (локальный фрейм → внешние контексты → глобальная область).
* **Анонимные функции**: при создании анонимной функции (`@(x) x + a`) ядро выполняет снимок (snapshot) текущих значений захваченных переменных по значению (через COW). Это гарантирует предсказуемость семантики без побочных эффектов при изменении внешних переменных после создания функции.

### 6.2. Объектная модель (`OBJECT_MODEL.md`)
Ядро поддерживает классы, создаваемые через `classdef`, и встроенные C++-классы (`BuiltinClass`):
* **Value Classes vs Handle Classes**: флаг `objIsHandle` в `HeapObject` определяет семантику копирования. Для Value-классов копирование приводит к COW-дублированию внутреннего состояния `ObjectState`. Для Handle-классов (наследников `handle`) копируется только `std::shared_ptr<ObjectState>`, обеспечивая ссылочную семантику.
* **Единая диспетчеризация**: индексирование (`obj.prop`, `obj(i)`, `obj.method()`) обрабатывается унифицированными хуками `tryObjectBinaryOp` и `resolveSubsrefChunk`, гарантирующими единое поведение на VM и TreeWalker.

## 7. Резюме ключевых инженерных решений

| Задача | Архитектурное решение в `numkit` | Преимущество |
|---|---|---|
| **Аллокация скаляров** | 16-байтовый тегированный указатель (`Value`) | 0 аллокаций на куче для чисел `double` и логических типов |
| **Копирование массивов** | Атомарный Copy-on-Write (`HeapObject`) | Мгновенное присваивание (`B = A`) без дублирования памяти |
| **Изоляция ядра** | Строгое правило `core ⊥ compute` + линтер слоев | Возможность линковать математику в C++ без интерпретатора |
| **Надежность исполнения** | Dual Engine (Bytecode VM + TreeWalker fallback) | 100% паритет, автоматическое резервирование при сбоях JIT/компилятора |
| **Отладка в WASM** | Нерекурсивный явный стек фреймов в куче | Полная поддержка breakpoints/step в WebAssembly без Asyncify |
| **Память приложений** | Поддержка C++17 `std::pmr::memory_resource` | Интеграция с кастомными аренами и пулами памяти хоста |
