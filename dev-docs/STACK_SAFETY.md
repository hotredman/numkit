# Безопасность стека: неограниченная вложенность входа роняет процесс

*Status:* **fixed** · *Found:* 2026-08-29 · *Repro:* `main` @ `c369399b`,
сборка `build/desktop-fast` (MSVC, Release; ядро `src/core` на HEAD идентично
протестированной сборке) · *Kind:* crash — пользовательский ввод убивает
процесс/модуль без диагностики.

## Резюме фикса

Реализована двухуровневая защита от переполнения стека и крахов `0xC00000FD` / `SIGSEGV`:
1. **Слой 1 (Parse-time Nesting Limit, UX)**: RAII `NestingGuard` в `Parser` с лимитом `MAX_NESTING_DEPTH = 200`. Защищены все точки рекурсивного спуска (`parseExpression`, `parsePrimary`, `parseStatement`, `parseBlock`, `parseIf`, `parseFor`, `parseWhile`, `parseSwitch`, `parseTryCatch`, `parseArrayLiteral`, `parseMatrixLiteral`, `parseCellLiteral`). Выдаёт чистую ошибку парсинга с номером строки и столбца.
2. **Слой 2 (Физический водяной знак стека `StackGuard`)**: Кроссплатформенный `numkit::StackGuard::check(stage)` с порогом запаса 64 КБ (`GetCurrentThreadStackLimits` на Windows, `emscripten_stack_get_free()` на WASM, `pthread_attr_getstack` на POSIX). Установлен во все рекурсивные обходчики (`Compiler::compileNodeExpand`, `TreeWalker::execNodeExpand`, `TreeWalker::execBlock`).
3. **Слой 3 (Верификация & Тесты)**: Добавлены модульные тесты в `src/core/tests/parser_test.cpp` (`ParserNestingLimitTest`) и `tests/gtest/integration/error_diagnostics_test.cpp` (`DualEngineTest`). Все тесты успешно проходят на обоих бэкендах (`TreeWalker` и `VM`).

## 1. Симптом

Вход с большой вложенностью даёт **три режима** поведения (пороги зависят от
сборки; цифры — desktop-fast Release, x86_64):

| вложенность `sin(sin(...))` | поведение |
|---|---|
| ≤ ~250 | выполняется корректно |
| 300–425 | чистая ошибка, exit 1: `Compiler: register exhaustion (>255 registers needed in chunk)` |
| ≥ 450 | **глухой крах**: exit `-1073741571` = `0xC00000FD` `STATUS_STACK_OVERFLOW`, stderr пуст |

Второй вектор того же класса — **вложенность блоков**: 5000 вложенных
`if 1 ... end` тоже роняют процесс с `0xC00000FD`, причём без «чистого» окна
в-between: у этого пути вообще нет промежуточного guard'а.

Ключевое: крах наступает **до** какой-либо диагностики. Это не «медленно» и не
«неверно» — это нарушение инварианта «любой вход либо исполняется, либо даёт
диагностику», который остальная часть проекта (см. soundness-контракты
codegen, `src/codegen/DESIGN.md` §10) считает базовым.

## 2. Воспроизведение

```bash
# Вектор 1: вложенность выражений (крах между 425 и 450 на этой сборке)
python -c "n=500; e='sin('*n+'1'+')'*n; open('build/deep_nest.m','w').write('y = '+e+'; disp(y);\n')"
build/desktop-fast/apps/numkit/Release/numkit_repl.exe build/deep_nest.m
echo $?   # 0xC00000FD / -1073741571

# Вектор 2: вложенность операторов (крах на ~тысячах)
python -c "n=5000; open('build/deep_if.m','w').write('y=1;\n'+'if 1\n'*n+'y=y+1;\n'+'end\n'*n+'disp(y);\n')"
build/desktop-fast/apps/numkit/Release/numkit_repl.exe build/deep_if.m
```

IDE открывает произвольные `.m`-файлы и принимает вставку в консоль — т.е.
вход контролируется пользователем целиком, одним Ctrl+V.

## 3. Диагностика (кто именно умирает)

**Парсер — невиновен.** `numkit_codegen` (парс + инференс + эмит, без
исполнения) обрабатывает n=1000 с exit 0: глубокий AST строится честно.
Краш — ниже по конвейеру.

**Место краха — рекурсивный спуск компилятора байткода.**
`Compiler::compileNode` / `compileNodeExpand` (`src/core/src/compiler.cpp:461`,
`:474`) рекурсируют на каждый уровень вложенности. Кадр ≈ 2.2–2.4 КБ
(стек Windows по умолчанию 1 МБ, `/STACK` в CMake не задан; 1 МБ / 425–450
кадров). Спуск умирает, **не дойдя** до внутренней проверки.

**Почему чистая ошибка есть, но срабатывает слишком поздно.** Регистры VM —
`uint8_t`, значит глубина вложенности > 255 в байткоде физически невыражаема;
компилятор это знает и бросает
`Compiler: register exhaustion (>255 registers needed in chunk)`
(`compiler.cpp:265`, `:356`). Но проверка срабатывает **на подъёме** рекурсии —
после того как спуск дошёл до дна. На n ≥ ~450 спуск до дна не доходит: стек
заканчивается раньше. Окно 255–~450 — зона, где диагностика успевает; выше —
труп процесса.

Отсюда важное следствие: **де-факто предел языка уже существует — 255** (для
VM-пути). Баг не в отсутствии предела, а в том, что он проверяется
пост-фактум, в середине конвейера, и не покрывает ни TreeWalker (у него нет
регистрового потолка — только чистая рекурсия `execNode`/`execNodeInner`/
`execBlock`), ни вложенность блоков, ни, потенциально, прочих обходчиков.

**Гарды глубины отсутствуют как класс**: `maxDepth|depthLimit` — 0 совпадений
в `parser.cpp`, `compiler.cpp`, `tree_walker.cpp`.

Рекурсивные потребители глубины user-контроля (все — кандидаты в §5, слой 2):

| Стадия | Точка рекурсии | Наблюдение |
|---|---|---|
| Parser | `parseExpression` ↔ `parsePostfix`/`parsePrimary` (`parser.hpp:80`,`:92`) | выживает ≥ 1000 (Release) |
| Compiler (байткод) | `compileNode` / `compileNodeExpand` (`compiler.cpp:461`,`:474`) | **крах ~450** |
| TreeWalker | `execNode` (`tree_walker.cpp:334`), `execNodeInner`, `execBlock` | нет потолка кроме стека |
| codegen | инференс + emitter | выживает ≥ 1000 (Release; в Debug не гарантировано) |
| Деструктор AST | `~ASTNode` → цепочка `unique_ptr` (`ast.hpp:84`) | кадры крошечные; в пределах лимита выживает |

## 4. Радиус поражения

- **Десктоп**: смерть процесса (REPL, скрипты, всё, что открывает файл).
- **WASM/браузер**: модуль собирается со стеком 4 МБ (`wasm/CMakeLists.txt:19`
  `-s STACK_SIZE=4194304`), но переполнение абортирует весь модуль/вкладку;
  бюджеты стека воркеров (`ide/src/sab-bridge`) зависят от браузера и должны
  валидироваться отдельно.
- **Debug-сборки**: кадры толще → порог краха ниже; любая фиксированная цифра,
  настроенная по Release, ложь в Debug (и наоборот) — см. §5, слой 2.
- **Оба движка**: TreeWalker не спасает даже регистровый потолок.

## 5. Правильный фикс — три слоя

### Слой 1 — контракт вложенности на этапе парсинга (UX)

Один RAII-счётчик глубины в рекурсивном спуске парсера; при превышении —
чистая ошибка парсинга с строкой/столбцом («expression nesting exceeds N
levels»). Лимит **≤ 255** и этим обоснован архитектурно (регистровый файл
`uint8_t`), а не магической цифрой; перед выбором конкретного значения
пробнуть MATLAB R2025b на глубокой вложенности — если его порог ниже, взять
его порог ради паритета (стандартный parity-проб проекта). Такой предел —
норма языка, а не костыль: nesting limit есть у MATLAB, Julia (скобки),
Python (`RecursionError` на parse), clang/V8 (stack guards).

Слой 1 закрывает и второй вектор (счётчик считает глубину спуска целиком —
выражения и операторы), и даёт **одинаковый** порог на обоих движках.

### Слой 2 — watermark-гард в каждом рекурсивном обходчике (инвариант)

Слой 1 — «приятно»; это — «правильно». Любую фиксированную цифру опровергнет
реальность: Debug-кадры толще, стек WASM-воркера меньше, debugger-режим жирнее.
Поэтому в каждый рекурсивный потребитель из таблицы §3 — крошечный RAII
`StackGuard`: адрес локальной переменной сравнивается с базой стека,
зафиксированной на входе в Engine; при запасе < порога (скажем, 64 КБ) —
чистый throw «nesting too deep in <stage>», который существующая обработка
ошибок покажет как обычную диагностику.

Свойства: ноль магических чисел (лимит физический, а не угаданный);
адаптивность к любому стеку (1 МБ main / 4 МБ WASM / воркер / Debug);
один хелпер — одна строка на стадию. Так делают clang
(`isStackNearlyExhausted`) и V8 (`StackLimitCheck`).

**Инвариант после фикса:** произвольная входная строка → AST + исполнение,
либо диагностика. Никогда — SIGSEGV/abort/stack overflow. Это в точности
философия soundness-контрактов codegen («refuse, never miscompile»),
применённая к ядру. Litmus-тест удаляемости: удалить слой 1 — слой 2 всё
равно предотвращает крах (ошибка просто менее изящная). Correctness ⊥ niceness.

### Слой 3 — регрессия

- gtest через `DualEngineTest`: глубокие выражения и глубокие блоки →
  `EXPECT_THROW` с диагностикой на **обоих** движках;
- запись бага по протоколу (`bugs/opened/lang/`, см. §9) + smoke;
- фаззер парсера/конвейера (генеративный минимум) как храповик: любой вход
  либо диагностится, либо исполняется — третьего не дано.

## 6. Анти-решения (что считать костылём)

- **`/STACK:16МБ` или выделенный глубокий поток** — заплатка симптома:
  воркеры WASM всё равно ограничены, деструктор AST и непройденные гардом
  рекурсии всё равно падают, контракта как не было, так и нет.
- **SEH `__except(STACK_OVERFLOW)`** — восстановление после переполнения стека
  ненадёжно (состояние стека не определено), в WASM SEH нет вовсе.
- **Итеративная переписка парсера/обходчиков на явный стек** — месяцы работы
  и риск регрессий на 11 тыс. тестов, при том что парсер — единственная
  стадия, которая не падает; остальных потребителей это не чинит. Даже
  clang/V8 не идут этим путём.
- **Счётчики глубины с разными цифрами в каждом потребителе** — разъедутся при
  первом рефакторинге; фиксированные числа опровергаются Debug/WASM-реальностью.

## 8a. Hardening-проход (2026-08-29, после `e8267458`)

1. **Watermark в парсере** — `NestingGuard` дополнительно вызывает
   `StackGuard::check("parser")`: на хостах с малым стеком (WASM-воркеры)
   спуск может исчерпать стек до срабатывания фиксированного лимита 200;
   теперь и этот путь даёт диагностику, а не краш.
2. **Кэш границы стека в POSIX-ветке** — `pthread_getattr_np` (локи/rlimit в
   glibc) вызывался на каждый узел AST в горячем пути TreeWalker; граница
   стека внутри потока не меняется — закэширована в `thread_local`,
   дальше только сравнение указателей.
3. **Механизм-тест слоя 2** — `src/core/tests/stack_guard_test.cpp`:
   рекурсия с гардом на каждом кадре обязана закончиться чистым
   `std::runtime_error` ДО аппаратной guard page. Закрывает пробел «слой 2
   недостижим через пользовательский вход при лимите 200 — покрыт только
   API-смоук»: теперь механизм доказан напрямую.
4. Прогон полного gtest-сьюта в Release и Debug — фикс и hardening
   верифицированы на всём корпусе, а не на целевых тестах.
